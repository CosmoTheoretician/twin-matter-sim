**New (6):**
- `gpu_backend.py` — torch import/availability, device & dtype resolution, `GPUParticles` (device-resident tensors with `from_host()`/`to_host()`), memory query and the pure-Python memory estimator used before a run.
- `forces_pm_torch.py` — `PMSolverTorch`: CIC deposit via `index_add_`, `torch.fft.rfftn/irfftn` Poisson solve, spectral gradient, CIC gather, periodic and isolated BC, 2-D and 3-D. It is built *from* a CPU `PMSolver` and copies that solver's kernel, k-arrays and self-potential to the device, so the scheme is bit-for-bit the same recipe.
- `integrator_torch.py` — `ForceEvaluatorTorch` (same interface as `ForceEvaluator`, accepts numpy `ParticleSet` *or* `GPUParticles`), torch adapters for the rigid external fields, torch `kick/drift/leapfrog_step/choose_dt` with the same expansion algebra (u = a²ẋ).
- `run_loop_gpu.py` — the time loop with particles resident on the device; host copies only at `log_every`, structure and snapshot cadences; same CSV/snapshot/summary outputs as `scenarios.run_loop`.
- `plotting_3d.py` — informative 3-D snapshots: per population, three projected log-density maps (xy, xz, yz) plus a thin mid-plane slice.
- `gputest.py` — the `gputest` command: CPU vs GPU forces on identical random particles in 2-D and 3-D (periodic + isolated, float32 and float64), relative errors, momentum check, timing per force evaluation, peak GPU memory.

## How the GPU path works

1. `resolve_defaults` sets `method='pm'`, `dtype='float32'` (unless `--dtype float64`) when `device='gpu'`; `--method direct --device gpu` is a configuration error (the direct sum stays CPU-only and remains the validated reference).
2. `main.py` prints the memory estimate (`gpu_backend.estimate_gpu_memory`) and stops if it exceeds the device total (16 GB), then dispatches as before.
3. `scenarios.build_forces` creates a CPU `PMSolver` (for the kernel and the rigid-ring field precompute) and wraps it in `PMSolverTorch` + `ForceEvaluatorTorch`. The initial conditions are built on the CPU exactly as now (they call the evaluator with numpy arrays; the evaluator uploads, solves, downloads).
4. `run_loop_gpu` uploads the IC once to a `GPUParticles`, integrates with torch leapfrog (KDK, expansion-aware), and only at logging/structure/snapshot cadences calls `to_host()` and feeds the ordinary `ParticleSet` to the unchanged `diagnostics_row`, structure functions and `snapshot`.
5. `gputest` quantifies the CPU/GPU agreement (expect ~1e-6 relative in float32, ~1e-12 in float64) and reports speed and memory, so a GPU run can be validated against the CPU reference before long runs.
